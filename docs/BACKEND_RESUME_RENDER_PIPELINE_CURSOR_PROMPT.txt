# Backend Cursor Prompt — Resume template storage + authoritative Render pipeline

Copy everything below to the backend agent/developer.

================================================================================
GOAL
================================================================================

Devora21 frontend no longer builds tailored DOCX/PDF files.

The backend must be the single source of truth for:

1. Stored resume templates (upload → templateId)
2. Applying structured resume content onto a stored template
3. Generating DOCX
4. Converting DOCX → PDF
5. Persisting DOCX + PDF + metadata relationships
6. Serving Preview and Download from stored files

Frontend responsibilities (already implemented):

- Upload template via multipart profile APIs
- Create/edit structured resume content (review UI)
- Call POST /resume/render with content + templateId
- Preview PDF via GET /resume/archives/{id}/pdf
- Download DOCX/PDF via existing archive/deliver endpoints
- One-shot still uses POST /resume/from-job (must reuse the SAME render pipeline)

Frontend API base: https://api.devora21.com (or NEXT_PUBLIC_API_BASE_URL)
Auth: session cookie and/or Bearer dv21_ key (same as other resume routes)

A) Template upload (existing multipart, extend response)

REQUIRED response fields (add if missing):

{
  "templateId": "<same id>",

Store the original DOCX bytes keyed by templateId + userId.
Do not rely on the frontend to keep the only copy.

A2) Template PDF preview (NEW — required for WYSIWYG "View template")

Browser HTML docx-preview cannot match Word. Frontend now prefers a backend PDF.

Implement ONE of:

  GET /auth/profile/resume-template/pdf
  GET /resume/templates/{templateId}/pdf

Behavior:
1. Load the user's stored original template DOCX
2. Convert DOCX → PDF with the same converter used by /resume/render (LibreOffice)
3. Return application/pdf bytes (or JSON { pdfBase64, pdfFileName })

Do NOT re-fill/analyze content — convert the original template file as-is.
Cache the PDF per templateId+updatedAt if useful.

================================================================================
RENDER PIPELINE (single authoritative implementation)
================================================================================

function renderResume(userId, templateId|bytes, content, jobMeta):

1. Authenticate user; enforce resume-builder access.
2. Load template DOCX:
   - if templateId: load stored original for this user
   - else if templateBase64: decode (transitional) and optionally persist as template
3. Validate/normalize content (title/summary/skills/experiences required).
4. Apply content onto template DOCX (preserve contact/header/layout; rewrite content sections).
   IMPORTANT: Port or share logic equivalent to frontend `applyContentToDocx` so
   bold title/experience headers, skills style, project vs bullets layouts stay correct.
5. Save generated DOCX on backend storage.
6. Convert DOCX → PDF (LibreOffice/soffice headless or current production converter).
7. Save generated PDF on backend storage.
8. Persist relationship:
   - userId
   - templateId
   - resumeId / archiveId
   - jobTitle, companyName, jobDescription
   - docx path/key + fileName
   - pdf path/key + pdfFileName
   - createdAt / updatedAt
9. Return ids + file metadata (and optional pdfBase64 for first paint).

Both:
- POST /resume/render
- /resume/from-job fill+render steps

MUST call this same pipeline.
